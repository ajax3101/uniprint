# Безопасность UniPrint

Документ задаёт предварительные требования к проектированию, а не подтверждает юридическое или инфраструктурное соответствие. До внедрения нужны классификация данных и оценка подразделения информационной безопасности университета.

## Данные и минимизация

- Пользовательские данные: устойчивый ID, имя для интерфейса, подразделение, роль и состояние учётной записи. Не переносить лишние кадровые поля.
- Данные заданий: идентификатор источника, принтер/очередь, время, доступные агрегаты и статус. Содержимое документов, spool-файлы, текст/имя документа не собирать по умолчанию.
- IP/MAC, учётные данные интеграций, фотографии и аудит имеют ограниченный доступ; в логах приложения секреты и чувствительные данные не дублировать.
- Заранее установить цели, сроки хранения, экспорт/удаление по правилам университета. Изобретать срок хранения нельзя.

## Доступ и идентификация

- Предпочитать университетский IdP/LDAP/AD после проверки реальных возможностей и политики; парольная локальная учётная запись, если нужна, требует проверенного хеширования и процесса восстановления.
- RBAC плюс проверка области: подразделение, собственные заявки, назначенные устройства и склад. Все API проверяют права на сервере.
- Администраторские и сервисные учётные записи разделены; минимальные разрешения, ротация/отзыв, MFA если доступно и требуемо политикой.
- Согласование фиксирует идентичность, роль, версию маршрута и отметку времени. Это само по себе не является электронной подписью или гарантией юридической значимости.

## Интеграции и сеть

- Коннектор направляет запросы только к allowlist принтеров/серверов; inbound доступ с устройств не требуется, если источник поддерживает опрос.
- SNMPv3 authPriv — предпочтительный вариант при поддержке и настройке университета. Запросы read-only; SNMPv1/v2c допустимы только по отдельному сетевому/ИБ решению и защищённому сегменту.
- Использовать IPPS/HTTPS и проверку сертификатов, если сервер/устройство их предоставляет. Секреты — в утверждённом хранилище; не в репозитории, образе и логах.
- Отдельные сетевые ACL, таймауты, лимиты опроса, защита от SSRF через произвольные адреса, журналирование ошибок без секретов.
- Никакого автообнаружения/массового сканирования без диагностики и отдельного разрешения.

## Приложение и данные

- TLS для веб-доступа, безопасные cookie/session, CSRF-защита при cookie-сессиях, контроль CORS, валидация входных данных, rate limits для авторизации и критичных операций.
- Параметризованные запросы; секреты окружения; отдельные роли БД для приложения и миграций; ограничение доступа к бэкапам.
- Вложения по умолчанию отключены до определения необходимости; если включены — ограничения размера/типа, антивирусная проверка по инфраструктурному стандарту, изолированное хранение, авторизация каждой загрузки/выгрузки.
- Журнал операций append-only на уровне приложения, корреляция и экспорт для аудита. Резервное копирование и тест восстановления обязательны до эксплуатации; одних логов недостаточно для неизменяемости аудита.
- QR-этикетка содержит случайный UUID-токен без персональных данных; создание SVG ограничено ролями склада/администратора, а операции по отсканированному токену всё равно проверяют авторизацию и состояние.
- Защита от повторного запроса: транзакции, idempotency key, уникальные ограничения и блокировки.

## Реализованный локальный режим

Пока IdP не подключён, production режим API закрывает все доменные маршруты (`503`). Временный `UNIPRINT_AUTH_MODE=development` принимает ID и роли из `X-Dev-*` заголовков только при loopback соединении; dev UI хранит только synthetic identity в `sessionStorage`. Роли при этом задаются заголовком, поэтому этот режим нельзя использовать вне локальной разработки. Команда `uniprint-dev-user` запрещена без явного development режима. Этот механизм не является аутентификацией для эксплуатации.

## Украина: правовой контекст

До запуска ответственные лица университета должны определить роли владельца/распорядителя персональных данных, правовое основание, информирование работников, объём/сроки хранения и допустимость индивидуальной аналитики. Отдельно проверить применимость актуальных редакций законов Украины «Про захист персональних даних», «Про електронні документи та електронний документообіг» и «Про електронну ідентифікацію та електронні довірчі послуги», а также внутренних актов учреждения. Этот документ не является юридическим заключением.

Официальные тексты: [закон о защите персональных данных](https://zakon.rada.gov.ua/go/2297-17), [об электронных документах и документообороте](https://zakon.rada.gov.ua/go/851-15), [об электронной идентификации и доверительных услугах](https://zakon.rada.gov.ua/go/2155-19).

## Реагирование и эксплуатация

До продуктивного запуска определить владельца системы и данных, уведомления об инцидентах, отзыв интеграционных ключей, восстановление, обновления, контроль уязвимостей и безопасное удаление. Не разворачивать приложение до согласования среды, сетевых правил и резервного копирования.
